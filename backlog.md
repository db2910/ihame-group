## Phase 1 — Auth, users, roles, customers, audit log — ✅ Built (4 Aug 2026)

**Stack:** Next.js 16 (App Router, TypeScript) + Prisma 7 (`@prisma/adapter-pg` driver adapter) + Supabase Postgres + Tailwind v4. See [[ihame-tech-stack]] memory for the full decision record.

**Data model:** `users`, `customers`, `audit_log` — plus infra tables not in the spec's own §4 (needed to actually implement §11): `sessions` (server-side, revocable — not a bare JWT), `password_reset_tokens` (schema ready, unused until email delivery exists — see simplifications), `auth_events` (login/logout/failure/reset/deactivation log, separate from `audit_log` per spec).

**Screens:**
- [x] Login — all roles (§6.1) — desktop + mobile responsive, pixel-matched to the mock
- [x] Users — manager only (§6.7) — list, add user, reset password, deactivate/reactivate
- [x] Audit log — manager only (§6.8) — filterable (table/user/date range), paginated, read-only
- [x] Nav chrome per role — dark sidebar (manager, 216px) / dark top bar (staff, 58px)
- [x] Customers — list/search screen + add/edit modal, shared between manager and freight staff with role-appropriate chrome
- [x] Change-password screen (forced first-login / post-reset flow — not separately spec'd, but required by §11's forced-reset rule)
- [x] Placeholder "coming soon" landing pages for every not-yet-built nav destination (Dashboard KPIs, All orders, Bulk status, Items, Purchases, Stock movements, Adjustments, Reports, My orders, New order, Sale, Today's sales, Stock lookup) so the full nav is clickable and no route 404s, without building phase 2–6 functionality early

**Rules/security implemented:**
- [x] bcrypt password hashing (via `bcryptjs`, pure-JS — no native build step), min length 10
- [x] httpOnly + Secure(prod) + SameSite=Lax session cookies; 30 min idle / 12 h absolute timeout, enforced against a DB-backed `sessions` table (not just a JWT expiry) so it's actually revocable
- [x] Login rate-limit: lock after 5 failed attempts / 15 min, checked by email and by IP independently, backed by `auth_events`
- [x] Generic "Invalid email or password" always for bad credentials/lockout; `is_active=false` gets its own distinct message per spec
- [x] Forced password reset on first login and after admin/manager reset; revokes all other sessions for that user
- [x] Deactivating a user revokes active sessions immediately
- [x] No self-registration — manager creates all accounts; manager also can't deactivate their own account (unrecoverable-lockout guard, not spec'd but necessary)
- [x] Role matrix (§2 + `src/lib/authz.ts`) — every Server Action re-checks role itself, not just the page-level gate (defense in depth per §11's explicit instruction)
- [x] `audit_log` treated as append-only at the application layer; DB-level `REVOKE UPDATE/DELETE` still to do at deployment time (see Simplifications)

**Simplifications made building this (flagging since they weren't literal spec readings):**
- **Temporary passwords are generated, not typed by the manager.** §6.7 lists "temporary password" as a form field; we generate a compliant random one and show it once instead, since a manager typing one live risks weak/reused values on the most-attackable moment (a brand-new account). Same mechanism for admin-triggered resets.
- **"Reset password" and "Forgot password" don't use the `password_reset_tokens` table yet.** There's no email sending set up, so a manager-triggered reset just generates+shows a new temporary password directly (same UX as account creation) instead of an emailed link. The login page's "Forgot password" link shows a static "contact your manager" note. The token table exists in the schema for when email delivery is added.
- **Customer code prefix is a fixed `KGL-####` sequence**, not per-destination as the spec's one example (`KGL-0412`) implies — see Phase 0 decision above for why (no destination context exists on a standalone Customers screen, and a customer isn't tied to one destination over their lifetime anyway).
- **Audit log export (Excel/PDF) is not built.** Spec §6.8 calls it "exportable"; treated as belonging with the Phase 6 reporting/export infrastructure rather than duplicating export logic early.

**Exit criteria:** met — all account types log in and land on the correct screen for their role; manager can create/deactivate users; every mutation has an attributable audit trail in place before other modules start writing to it.

**Second round of real-device fixes (4 Aug 2026):**
- **Hamburger did nothing on the phone — not a UI bug at all.** `next dev` only serves `/_next/*` dev assets to the host it was started on and 403s every other origin, so loading the LAN URL (`http://192.168.1.75:3000`) on a phone returned HTML with **no JavaScript**: the page rendered server-side and looked fine, but React never hydrated, so every `onClick` in the app was dead. Fixed with `allowedDevOrigins` in `next.config.ts` (private-network ranges). Development-only; production was never affected. Reproduced and verified by driving the LAN URL in a real browser — 403s on the chunk requests before, drawer opening after.
- **The "Sign in" ghosting was real, and it was an overlap.** The login photo panel was a hard `h-[252px]` box whose *last* child (the phone-only "Freight and shop, one ledger." headline) sat after a `h-full` sibling, so it overflowed ~88px past the panel and landed on top of the white card — white 26px text painted directly over the dark "Sign in" heading at the same x. Confirmed by measuring boxes (headline `y 252–340`, heading `y 280–308`), not by eyeballing a screenshot. The panel is now content-height with `min-h-[252px]` and its artwork/gradient in an absolute layer, matching how the mock actually composes that screen, so nothing can overflow it again.
- **Login panel placeholder artwork** — `public/assets/login-backdrop.svg`, a China → Kigali corridor abstraction over a container yard, drawn to survive both crops (tall 600px desktop column, short 390×252 phone strip). Phase 0's "keep the placeholder" decision stands; swapping in a real depot photo later is a one-line change to `PANEL_IMAGE` in the login page.
- **Redirect loop that locked the user out of the login page.** The session cookie's JWT lives for the 12h absolute timeout, but the DB session dies after 30 min idle (or on revoke/deactivate), so for most of that window the cookie verifies in `proxy.ts` while resolving to "signed out" in the DAL. The proxy bounced `/login → /` on the cookie alone, the root page's DAL check bounced `/ → /login`, and the browser gave up with `ERR_TOO_MANY_REDIRECTS` — no way back to the login form except manually clearing cookies. Reproduced with a valid-signature/dead-session cookie (12 hops and still cycling), fixed by making the proxy strictly one-directional: a valid signature lets a request *through* to the real check but never redirects anyone *into* the app. Signed-in users are still sent off `/login`, by the login page itself, which knows whether the session is actually alive. The proxy now also clears an unverifiable cookie on its way out, and the matcher excludes all of `/_next` (it was catching `/_next/hmr`).
- **Form side no longer a flat grey field** — new `AuthBackdrop` (fine engineering grid faded at the edges, brand/accent radial glows, centre lift) sits under the card on both the login and change-password screens, plus a seam hairline and a small `IHAME LOGISTICS & SUPPLY LTD · KIGALI, RWANDA` footer on the login's desktop layout.

**Third round of mobile fixes (12 Aug 2026), requested directly — "on small devices make the navbar sticky":** confirmed live before touching anything (`getBoundingClientRect().top` on the mobile top bar going from `0` to `-600` after a 600px scroll) that neither shell actually scrolls its *content* internally — nothing in either layout bounds `<main>` to the viewport height, so the whole document scrolls and drags the "fixed" top strip off-screen with it. Rather than rework that deeper container-height question across every page, both mobile headers (`ManagerShell`'s hamburger strip, `StaffTopBar`'s header) got `position: sticky; top: 0`, which pins correctly to the real scrolling container (the document) regardless of whether it's the whole page or an inner region doing the scrolling. `StaffTopBar`'s header is shared across every width (unlike the manager shell's mobile-only strip), so it's `sticky` only below `md` (`md:static`) — scoped to what was actually asked, desktop untouched. Verified: top bar stays pinned at `top: 0` through a real scroll on both shells, the hamburger drawer still opens correctly over the now-stuck header with no z-index conflict, no new horizontal overflow, and `StaffTopBar`'s computed `position` at desktop width confirmed back to `static`.

**Tenth round — Opening stock import built (8 Aug 2026), Phase 2 complete:**

Built to the Phase 2 decision above, with CSV and manual entry unified into one flow rather than two separate paths: uploading a CSV parses it **client-side** and populates the same editable row table manual entry uses, so a manager reviews and can correct every row before anything touches the server, and there's exactly one server code path to validate instead of two.

- `src/lib/csv.ts` — a small hand-rolled RFC4180-ish parser (quoted fields, embedded commas/newlines, escaped quotes), not a dependency — the only input is a manager's own spreadsheet export, not an arbitrary CSV dialect. Header-driven (`sku,name,category,unit,sellPrice,reorderLevel,quantity,unitCost`, matched case-insensitively with a few aliases like "sell price"/"cost"), not positional, since a manager's own column order won't reliably match one fixed layout. A "Download CSV template" button (client-side `Blob`, no server round trip) shows the expected shape.
- `src/app/opening-stock-import/actions.ts` — `importOpeningStockAction`: validates every row, pre-checks for duplicate/existing SKUs before touching the database (a specific "Row 3: SKU already exists" beats a raw constraint failure partway through a 50-row transaction), then in one transaction upserts categories by name, creates every item, and writes one `opening` stock movement per item tagged `reference_type="opening_import"`. Blank-SKU rows get sequential `ITM-####` codes allocated in one batch query (`generateItemSkus`, extended from the single-SKU suggester `src/lib/item-sku.ts` already used by Add-item) rather than one query per row.
- **The one-time lock has no settings table** — it's "does any `stock_movements` row have `reference_type="opening_import"`", re-checked both before building the page (server-rendered locked view vs. the form) and again inside the write transaction (closes the race between the two, even though the realistic odds of two managers hitting this once-ever screen simultaneously are near zero). Deliberately a different signal than "does any `opening` movement exist" — the regular Add-item form already writes plain `opening` movements for new items going forward, and that has to keep working after this screen locks itself out.
- **Nav entry added** (`manager-shell.tsx`, SHOP group, right after Items) — this screen had no placeholder route or nav entry from Phase 1's original sweep, unlike every other Phase 2/3+ destination. Added now rather than leaving it unreachable except by typing the URL.

**Eighth round — costing model simplified to last-purchase-price, Purchases made editable (7 Aug 2026):**

Triggered by the user asking why weighted-average costing existed at all, given it was the whole reason a "correct a wrong purchase" tool was turning into a large, fragile piece of engineering (reconstructing historical cost state, reasoning about compounding). Traced it to its only real consumer: Phase 6's planned "profit per item" and "stock on hand & value" reports. **Decision: drop those two report line items in favour of one aggregate "overall profit" figure (sales revenue − purchase spend, cash-basis)** — see Phase 6's scope-decision note for the full reasoning and the cash-basis caveat that comes with it. That removed the only reason `cost_price` needed to be historically precise, so:

- **`cost_price` changed from a weighted average to last-purchase-price** (`src/lib/stock.ts`'s `weightedAverageCost` replaced by `recomputeCostPrice`: look up the most recent `opening`/`purchase` movement, use its unit cost). Stateless — no history to reconstruct, no compounding, so correcting any purchase is now just "fix the number."
- **Purchases are now editable** (`updatePurchaseAction` alongside `createPurchaseAction`, both in `src/app/purchases/actions.ts`) — reverses the original "never edited" design now that nothing downstream compounds off a purchase's cost. The Purchase detail modal gained an "Edit" action opening the same line-editor form used to create one (`EditPurchaseModal` in `purchase-form-modal.tsx`, sharing its `LineRow`/`SupplierField`/`LinesEditor` internals with `RecordPurchaseModal`). Edits are logged to `audit_log` (header fields — supplier/date/purchase no./total) same as Items.
- **Schema: `stock_movements.purchase_item_id`** (migration `20260807090445_purchase_item_link`, nullable unique FK to `purchase_items`) — added because `reference_id` alone (shared by every line in the same purchase) can't identify *which* line's ledger row to update, and breaks outright if a purchase buys the same item on two lines (which the create form already allowed). Editing an existing line now updates its linked `stock_movements` row directly (`quantity`/`unit_cost`/`created_at`) instead of reversing and re-inserting — deliberately not append-only for this one case, since last-purchase-price costing has nothing left to protect by keeping the old row around. Existing demo purchases were backfilled to the new link by matching `(reference_id, item_id)`, verified safe first by confirming no purchase had two lines for the same item.
- **Real bug found and fixed while building this: purchase-date timezone drift.** `new Date(\`${dateString}T00:00:00\`)` parses as *local* midnight on whatever timezone the server runs in (this dev machine: `Africa/Kampala`, UTC+3), while the edit form's date input was pre-filled via `.toISOString().slice(0, 10)` (UTC). Under weighted-average costing this was latent and harmless — a purchase was written once and never read back through the form. The moment purchases became editable, every edit silently rolled the date back a day (confirmed live: a purchase edited twice drifted two days). Fixed by parsing and formatting purchase dates in UTC explicitly everywhere (`parsePurchaseDate` in `actions.ts`, `timeZone: "UTC"` on the list's date formatter) — now round-trips stably through repeated edits, verified by editing the same purchase twice with no changes and confirming the date input read identically both times.
- **Demo data reseeded, not hand-patched.** Two issues in `seed-demo.ts` needed fixing regardless of the edit-testing that surfaced them: it still computed weighted-average costs (updated to last-purchase-price, matching the real app), and its opening-stock movements were timestamped at seed-run time while purchase movements were correctly backdated — meaning openings looked *more recent* than the purchases that followed them, so the demo catalogue's costs told a confusing story. Opening movements now backdated 40 days (safely before the earliest demo purchase, 27 days). Fixed the live database by running `--reset` then reseeding fresh rather than trying to hand-correct data three test rounds had already left in an inconsistent state.
- **Items screen wording updated** (`item-form-modal.tsx`, `items-table.tsx`, and their surrounding comments) — every "weighted average" reference now correctly says "most recent purchase."

**Verified 7 Aug 2026:** the dev server needed a manual restart mid-session — it had the pre-migration Prisma Client loaded in memory from before `prisma generate` ran, which made every DB query (including login) hang indefinitely. Restarted cleanly, then drove the real app via a throwaway manager account (Playwright, desktop + iPhone): edited an existing demo purchase's line (quantity + unit cost) and confirmed, directly against the database, that the linked ledger row updated in place (not duplicated), on-hand summed correctly, `cost_price` matched the new unit cost exactly, and the audit log recorded the total change. Separately tested removing a line and adding a different item's line in the same edit — confirmed server-side (the detail view I screenshotted immediately after turned out to be stale from clicking too fast, not a real bug) that the removed line's ledger row was deleted, the new one created and linked, and both items' costs recomputed correctly. `tsc` and lint clean throughout. Cleaned up by resetting and reseeding the demo dataset (see above) and deactivating the throwaway account (audit_log rows referencing it block a hard delete, by design — same rule the app already applies to real users).

**Phase 3 decisions (confirmed with the user, 8–9 Aug 2026):**
- **Under-price sales get a real per-line price override in the cart.** The pixel mock's cart rows only show a read-only price next to the qty stepper — no field to actually charge less than list. Built one anyway, since without it the spec's "selling below sell_price permitted but flagged" rule could never actually trigger.
- **Proof-of-payment is a stub this round** — `sales.has_proof_of_payment` is a plain boolean, no file is actually stored anywhere. There was no upload/storage code anywhere in the repo to build on (no `sharp`, no Supabase Storage client, no S3), and real storage (private folder outside the public web root, metadata stripped, served through an authenticated route) is already formally scoped as Phase 7 hardening — building a throwaway version now just to redo it properly later was rejected.

**Follow-up fix (12 Aug 2026, from real counter testing with a large cart):** `attemptCompleteSale` ran one `stock_movements` aggregate query per cart line, sequentially, inside the transaction — fine for the small carts every earlier round tested with, but a real 7-line cart (one line qty 50) drove the transaction to 21+ sequential round trips against the hosted Supabase DB and expired Prisma's 5s interactive-transaction timeout (`P2028`), surfacing to the cashier as a bare "Could not complete the sale." Verified against the real DB with a 10-line cart rolled back inside an intentionally-failing transaction (no data persisted): completed in 1.4s, comfortably under both the old and new limits.

## Phase 4 — Freight order form, draft/submit lock, payments — ✅ Built (9 Aug 2026)

**Data model:** `orders`, `order_payments`, `order_status_history`, `order_vehicles` — migrations `20260808234039_phase4_orders`, `20260808234526_phase4_orders_nullable_draft_fields`, `20260809160000_phase4_order_vehicles`: new `GoodsCategory`/`Destination`/`Currency`/`OrderStatus` enums, `order_payments.method` reuses Phase 3's existing `PaymentMethod` enum rather than duplicating it. `goods_category` through `total_amount` are nullable at the DB level (see decision below), `vin` is globally unique. Verified against the real Supabase DB inside a rolled-back transaction before any UI existed: order/payment/status-history creation, the balance formula, and VIN uniqueness.

**Scope decision (9 Aug 2026):** this phase covers the **freight staff side only** — create, save-draft, submit, record payments, view own orders. The manager's full edit view, status-change control (in transit/arrived/delivered/cancelled), and cancel-with-reason are explicitly Phase 5 work per this backlog's own original framing ("carried over from Phase 4... this is where it's actually built") — building them now would mean building the manager dashboard's surrounding context twice. `order_status_history` is already wired for it: every future status transition just adds a row the same way draft→submitted does here.

**Phase 4 decisions:**
- **`goods_category`, `description`, `origin_port`, `destination`, `currency`, and `total_amount` are nullable columns, not defaulted.** Spec §5 "save draft validates only the customer" means a brand-new draft can genuinely have nothing else filled in yet — faking a default (e.g. `destination: kigali`) so a NOT NULL constraint would hold felt like inventing a business decision nobody made. `submitOrderAction` enforces all of them non-empty before status can move past draft; storage stays honest about what's actually known.
- **Order numbers are silently auto-generated, not a form field.** Unlike Purchases' human-suggested-and-editable `purchase_no` (which exists to match physical paperwork), nothing in the spec ties an order number to an external document, and freight staff have no reason to pick one. `generateOrderNo()` follows Purchase/Customer's read-then-format sequencing (`ORD-{year}-####`), not Sale's whole-transaction-retry pattern — order creation is a full-page deliberate action by one staff member at a time, not a high-frequency counter.
- **Balance never applies a payment's `exchange_rate`.** Spec §4's formula is literally `total_amount − SUM(order_payments.amount)` — no conversion. `exchange_rate` is stored per payment purely for Phase 6's combined-currency reporting; the payment form defaults a payment's currency to the order's own currency to keep mismatches rare, but doesn't block a different one.
- **Proof-of-payment is a stub, same as Phase 3's sales** — `order_payments.has_proof_of_payment` is a boolean, not a real file. Consistent with the already-confirmed Phase 3 decision; real storage is Phase 7 work.
- **Customer-add reuses the existing Customers screen's own action and modal fields** rather than a parallel implementation — `createCustomerAction` now also returns the created customer on success (additive field, doesn't change the Customers screen's own usage) so the order form can auto-select it immediately.

**Corrections after the first build (9 Aug 2026) — the design mocks had been missed.** §6.9–6.11 *are* pixel-mocked, in `dashboard-and-login-ui-design/project/IHAME Login and Dashboard.dc.html`. The first pass only searched the sibling `IHAME System UI.dc.html` (whose single titled section is the login + manager dashboard), found nothing freight-related, and built from the spec's field lists instead — despite this backlog already saying "**Mocked**" against all three screens, which should have been treated as proof they existed. What changed on the second pass:
- **Followed the mock**: `← My orders` back link, tinted status pills (the mock's own `pill` colour map — its hexes already match this project's brand/warn/success/delivered tokens), the amber "fields are locked" banner, the 1.5fr/1fr detail split, the dark **Agreed total / Paid / Balance** card with a paid-progress bar, proof-image tiles on payments, the dashed "+ Record a payment" button, status history with timestamps and author, numbered blue section headers on the form, the order-no + DRAFT badge, goods category as a **segmented control** instead of a `<select>`, 4-column field grids, and the emphasised Agreed-total input.
- **`container_no` and `bill_of_lading` had no UI at all** — both existed in the schema and the first migration but were never put on the form or the detail view, so there was no way to enter or read them. Caught only because the mock shows them.
- **`order_vehicles` split out of `orders` (new migration).** The spec models `make`/`model`/`year`/`colour`/`vin`/`engine_no` inline on `orders` alongside `quantity int default 1` — which silently only works for a single vehicle. An order shipping three cars needs three VINs, and `vin` is globally unique, so one-VIN-per-order is not just cramped but wrong. Vehicle detail now lives in a child table with one row per unit of `quantity`; the form renders that many blocks, driven by the quantity field. Submit validation requires a VIN for **every** vehicle and rejects a VIN repeated within the same order. The migration back-fills existing inline data into the new table *before* dropping the old columns, so nothing was lost.
- **Optional "5 · Payment received" section on the order form — a deliberate deviation from the mock**, which states payments are only recorded after saving. A customer routinely pays a deposit at the moment the order is raised, and forcing save → reopen → record was needless friction. Leaving the amount blank records no payment; the same required-unless-cash proof rule applies. The order's own Record-payment modal remains for everything after that.
- **Balance was never an input** and still isn't — it's `total_amount − SUM(payments)` computed at read time. It just wasn't *visible* where it mattered, so it now appears in the dark totals card, in the Record-payment modal, and as a live figure the form's helper text points at.

**Bugs found and fixed while building this:**
- **The shared `Modal` component didn't portal its content** — it rendered inline wherever it was mounted. Every prior use was a top-level page/table action, so this never mattered until the New-order form's inline "+ New customer" button put a `<Modal>` (containing its own `<form>`) *inside* the order form's own `<form>` — invalid nested-`<form>` HTML, and the browser resolved the inner submit against the wrong form entirely. Fixed by portaling `Modal` to `document.body` via `createPortal` — this is a shared component, so the fix protects every current and future modal-in-a-form case, not just this one.
- **Portaling then exposed a second, subtler issue**: React bubbles events along the *component* tree, not the DOM tree, so the portaled customer modal's own form-submit event still reached the order form's submit handling even though it's no longer a DOM descendant. Fixed with an `e.target !== e.currentTarget` guard in the order form's submit handler.
- **React resets every uncontrolled field in a `<form action={fn}>` after *any* `useActionState` action completes — success or error.** Fine for a small modal that closes on success (nobody sees the reset); actively wrong for a long multi-section form where a validation error ("fill in: VIN") should let the user fix just that one field. A failed submit was wiping the entire New-order form back to blank, VIN error and all, so retrying looked like it silently lost everything already typed. Fixed by switching `OrderForm` to a manual `onSubmit` handler that builds `FormData` itself (with the clicked submit button's `name="intent"` passed explicitly via `FormData`'s submitter argument) and calls `useActionState`'s dispatch inside `startTransition` — this bypasses React's automatic form-reset entirely, since that behavior is specifically tied to the `<form action={...}>` native-submission path, not to calling the dispatch function directly.
- **Editing an already-saved draft (same URL before and after) didn't visually refresh on success** — `router.push()` to the URL you're already on is a no-op in the App Router, so without an explicit `router.refresh()` the page kept showing stale content after a save. Fixed by calling `router.refresh()` unconditionally on success, and keying `<OrderForm>` to the order's `updatedAt` so a save forces a clean remount with the freshly-saved values rather than leaving old uncontrolled-input state on screen.
- **`uniqueConstraintMessage`/`isSaleNoConflict`'s error-shape check was silently broken for every caller, including the pre-existing Phase 2/3 ones.** This project's driver-adapter setup (`@prisma/adapter-pg`) reports a P2002 unique-constraint violation's column(s) at `meta.driverAdapterError.cause.constraint.fields`, not the classic engine's `meta.target` — the only place any of these three functions ever checked. Every real collision was silently falling through to the generic "That value is already in use." message instead of the specific one, in Purchases and Sale as well as this phase's own new order/VIN check — caught here because this was the first time a duplicate-VIN scenario was actually driven through a real browser rather than just unit-style. Fixed with one shared `src/lib/prisma-errors.ts` helper that checks both shapes, used by all three call sites now.

**Verified 9 Aug 2026:** two throwaway freight_staff accounts driven through real Chrome (`channel: "chrome"`) at desktop and 390px viewports. Confirmed end-to-end against the real Supabase DB: a draft saved with only a customer persists correctly; submitting with missing fields returns the specific friendly error and — after the form-reset fix — preserves everything already typed; submitting a vehicle order without a VIN is blocked, with one specific and one duplicate-VIN order confirming the uniqueness check's correct message; a full submit writes every field, flips status, and inserts exactly one `order_status_history` row (`draft → submitted`); recording a payment inserts the correct row and the balance recalculates correctly at read time (`12000 − 5000 = 7000`, confirmed both in the UI and by querying the DB directly); a second freight staff account sees zero orders in My orders and gets a 404 hitting the first account's order URL directly. Inline customer creation from the order form works and auto-selects the new customer. Record-payment modal renders correctly as a mobile bottom sheet. Zero console/page errors across the entire run after the fixes above. `tsc`, lint, and `next build` clean. All test accounts, orders, payments, and customers were created and deleted directly against the real Supabase DB; the three pre-existing real/prior-session accounts were identified and left untouched.

**Round 5 — Bulk status update.** `bulkChangeOrderStatusAction` — one DB transaction per bulk action (all selected orders move, or none do), one `order_status_history` row per order. One subtlety that mattered: the countdown's cleanup only tears down the cosmetic `setInterval` on unmount, never the underlying `setTimeout` — switching the status filter chip remounts the list (`key={status}`), and that's just changing what you're looking at, not a cancel; only clicking Undo itself should cancel a pending action. Also added a proper error-styled variant to the shared `Toast` component (`type: "error"`, red `⚠`, stays up longer) — every prior toast in the app was success-only, and a failed bulk action was rendering its error message with a success checkmark before this.

### Proof-of-payment storage — ✅ Built (12 Aug 2026)

Replaces Phase 3/4's `has_proof_of_payment` boolean stub on `sales` and `order_payments` with a real image: `proof_of_payment_path` (nullable string — null means no proof attached, required for every payment method except cash, enforced in each action). Migration hand-written directly in `prisma/migrations/` and applied via `prisma migrate deploy`, since `prisma migrate dev` (even `--create-only`) refuses to run non-interactively once it detects a column drop with non-null data — it exits before writing a file rather than prompting.

`src/lib/storage.ts` is the whole storage layer: a private Supabase Storage bucket (`proof-of-payment`), accessed via its plain REST API with `fetch` and the service-role key rather than pulling in `@supabase/supabase-js` for a handful of calls. Validation is by content, not extension or the browser's claimed MIME type — `sharp(buffer).toBuffer()` throwing *is* the validation, since a non-image genuinely fails to decode. `.rotate()` bakes in the EXIF orientation before metadata (including GPS) is stripped as a side effect of never calling `.withMetadata()`. Every upload is resized to 1600px max and re-encoded as JPEG (quality 82) before it's stored, capped at 8MB on the original. Three call sites upload through it: `completeSaleAction`, `saveOrderAction`'s optional initial-payment block, and `recordOrderPaymentAction` — all upload *before* their DB transaction starts (a slow external call has no business holding a transaction open), accepting the small trade-off that a sale/payment which fails validation after a successful upload leaves an orphaned image rather than engineering a two-phase commit for a payment-proof photo. Fetching back out goes through two authenticated Route Handlers (`/sale/[id]/proof`, `/orders/[id]/payments/[paymentId]/proof`) that re-check the session and the same role/ownership rules the rest of the app already applies (shop staff: today's sales only; freight staff: their own orders only) and proxy the bytes directly rather than handing back a public or signed URL that could be shared past its own access check. The bucket itself is private and holds no authorization logic of its own — access control is entirely these two routes' job, consistent with how the rest of the app already works.

**Real bugs found and fixed while building this:** (1) the `Buffer`-vs-`BodyInit` TypeScript mismatch from Phase 6's export routes recurred in `storage.ts` — same fix, wrap as `new Uint8Array(buffer)`. (2) Server Actions default to a 1MB request body; a real phone-camera photo comfortably exceeds that before `storage.ts`'s own resize/re-encode ever gets to shrink it — raised to 8MB via `next.config.ts`'s `experimental.serverActions.bodySizeLimit`.

### PWA offline queue — ⚠️ Built, partially verified (12 Aug 2026)

**Scope decision (12 Aug 2026):** offline sales are **cash-only**. MoMo/Bank/Card still require a proof photo and stay online-only, unchanged — a real outage usually means the customer's own mobile-money/card rails are unreliable too, and queuing a photo offline adds real complexity (local storage footprint, a bad photo only discovered far from the original sale) for a case that's already the minority of what a shop counter can actually take mid-outage.

`sales.client_request_id` (nullable, unique — hand-written migration, same non-interactive-refusal reason as the proof-of-payment one above) is the idempotency key underneath all of it: a UUID the POS generates the moment "Complete sale" is tapped, before it's known whether the request will reach the server. `src/lib/complete-sale.ts` is `attemptCompleteSale` pulled out of `sale/actions.ts` into its own module (also fixing a real bug in the same move — see below) so both `completeSaleAction` (any payment method, called directly while online) and the new `/api/sale/complete-cash` Route Handler (the offline queue's sync target) write a sale through the exact same validated path, and a retried submission of either one — the queue retrying after a lost response, or `experimental.useOffline` (now on project-wide in `next.config.ts`) replaying a Server Action once connectivity returns — hits the unique constraint and reads back the original sale instead of creating a second one.

`src/lib/offline/sale-queue.ts` is a small hand-rolled IndexedDB wrapper (one object store, keyed by `clientRequestId`) — not `localStorage`, since a queued sale needs to survive a reload mid-outage and hold a real record, not a string, and not capped at ~5MB shared with everything else on the origin. `src/lib/offline/offline-sync.ts`'s `flushQueue()` walks it strictly in order, stopping at the first network failure (preserving order for whenever connectivity actually returns) but setting a genuine server-side rejection (e.g. stock ran out) aside as "failed" and moving on, so one bad queued sale can't block every sale behind it. `pos.tsx` calls it on mount, on the browser's `online` event, and every 30s while the screen stays open — deliberately not the Background Sync API, which Chrome/Android support but Safari/iOS does not, so a shop counter can't actually depend on it firing in the background regardless of which phone is at the counter.

Tapping "Complete sale" on a cash sale now queues to IndexedDB first and clears the cart immediately — the cashier moves on to the next customer without waiting on the network at all — then attempts to sync in the background; the toast reflects whichever actually happened ("Sale SAL-0014 completed" if it synced fast, "Sale queued — will sync when back online" if it didn't). The catalogue's on-hand figures subtract whatever's already claimed by queued-but-unsynced sales, so several offline cash sales of the same item in a row can't all look available right up until they all fail together at sync time. A small manifest (`app/manifest.ts`) and a hand-rolled `public/sw.js` (opportunistic runtime caching for `/sale`'s navigation and `/_next/static/*` — not a full precache-manifest tool like Serwist, which Next's own docs point to for that; this only ever caches what was actually visited while online) round out the installability side and, when it works, let a reload survive mid-outage.

**Real bugs found and fixed while building this:**
1. **`attemptCompleteSale` ran a stock query per cart line, sequentially, inside the transaction** — harmless for a small cart, but a real 7-line cart (one line qty 50) drove 21+ sequential round trips to the hosted DB and expired Prisma's 5s interactive-transaction timeout, surfacing to the cashier as a bare "Could not complete the sale." Found from the user's own counter testing, not this phase's work — fixed here as part of extracting the function anyway. Rewritten to two upfront reads (`item.findMany` + `stockMovement.groupBy`, run concurrently) followed by `saleItem.createMany`/`stockMovement.createMany` — a fixed ~4 queries regardless of cart size — with per-line checks done in-memory against a running per-item deduction tally so a duplicate item across two lines still checks correctly. Verified against the real DB with a 10-line cart rolled back inside an intentionally-failing transaction: 1.4s, comfortably under both the old and new (10s) limit.
2. **The auth proxy redirected `/sw.js` to `/login` for a signed-out request**, which doesn't just look wrong — browsers hard-refuse to register a service worker whose script response is a redirect (`SecurityError`), so this silently broke registration outright. `src/proxy.ts`'s matcher now excludes `sw.js`, `manifest.webmanifest`, and the two icon files alongside its existing `_next/`/`assets/`/`favicon.ico` exclusions.

**Verified 12 Aug 2026, against a real production build (`next build && next start` — Next's own docs are explicit that dev mode isn't a reliable reference for offline behavior) via a throwaway `qa-phase7-shop@ihame.test` account and Playwright's `context.setOffline()`:** queuing multiple cash sales while offline works correctly — each lands in IndexedDB immediately with the right lines/total, the cashier is never blocked from ringing up the next one, and the UI's pending-sync indicator shows them accurately. The idempotency replay is confirmed race-safe: POSTing an already-synced `clientRequestId` a second time returns the original sale (`200`, the same `saleNo`) and the `sales` table still holds exactly one row for it. A queued sale that genuinely fails server-side (tested by queueing an impossible quantity directly, bypassing the client's own guard) is correctly marked "failed" with the real rejection reason shown, dismissible, and doesn't block the rest of the queue.

**Not yet confirmed working: automatic sync on reconnect.** Two isolated Playwright runs disagreed with each other — the queue and the idempotency guarantees are solid on their own, but I haven't yet nailed down why `flushQueue()` doesn't reliably fire once `online` is triggered in the test harness itself (it may be a Playwright/headless-Chrome quirk around how `context.setOffline(false)` fires the `online` event versus a real device's radio actually reconnecting, or a real bug in the effect's listener — undetermined). Manually reopening the POS screen (which flushes on mount, not just on the `online` event) is a reliable workaround in the meantime. **Flagged explicitly rather than silently shipped as "done"; needs a real-device check (not just headless Chrome) before this is trusted unattended.**

**Not built this round:** automated encrypted backups, HTTPS/HSTS (automatic on Vercel, the confirmed host — nothing to build), DB-at-rest encryption (Supabase's default — nothing to build), column-level encryption (still an open "consider," needs an explicit yes/no), CSRF review, alerting (needs a chosen outbound channel — none exists yet), firewall (N/A on serverless).

**Exit criteria:** the shop counter keeps taking sales through an internet/power outage and syncs cleanly afterward without duplicate sales; a real backup has been restored and verified, not just configured. **Partially met** — taking sales through an outage and avoiding duplicates on sync are both verified; automatic sync-on-reconnect specifically needs the real-device check noted above before this can be called met in full.
